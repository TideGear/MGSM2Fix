MGSM2Fix · reverse-engineering note

English text for Integral, discs 1 & 2

Every pause-menu weapon and item description in Metal Gear Solid lives in the boot executable, in two pointer tables. Integral’s tables have the same shape as the USA release’s, the same control codes, and more room than the English text needs — so the text itself is a data swap. Getting it into the running game is the hard part, and it is not a disc patch.

5 executables analysed item text: confirmed in-game stage container: solved 6 patches built

What the investigation found

  1. The text is only in the boot EXE. SLPM_862.47 (disc 1) and SLPM_862.48 (disc 2) are byte-identical, so one payload covers both discs. A scan of both STAGE.DIR archives (75 MB Integral, 72 MB USA) found zero records of this format — nothing to chase in the stage overlays.
  2. The record format is identical between builds. Same B014/D015 field markers, same 807C line break, same 90xx button glyphs. Every escape code the English text uses already appears in Integral’s own Japanese strings, so no font, glyph or renderer work is required.
  3. English is smaller than Japanese. 2,498 bytes of English against 2,982 bytes of Japanese. Repacking the two pools leaves 272 and 168 bytes spare.
  4. MGS1 (USA) alone covers all 36 records. VR Missions (USA) is not needed as a donor for discs 1–2 — it carries fewer strings. Its real value is elsewhere; see what VR Missions is actually for.
  5. The PPF was always fine; the timing of Ketchup’s RAM mirror was not. By the time any patch is applied the executable is already resident in RAM, loaded from a ROM snapshot rather than read off the CD, so patching the CD image changes nothing — and the mirror that could reach it fired too early and was discarded. Deferring that mirror fixes it, and the same PPF file then works unchanged. Done and confirmed in-game; see getting bytes into the game.

Where the text lives

Two arrays of 32-bit pointers into the executable’s data, plus one string reached directly from code. Addresses are PSX RAM; all five executables load at 0x80010000, so file offset = address − 0x80010000 + 0x800.

Both disc pairs ship the same executable twice, verified byte-for-byte: Integral 641,024 bytes identical, USA 651,264 bytes identical. The tables therefore sit at the same addresses on disc 1 and disc 2.

The record format

One NUL-terminated record holds both the display name and the description. Bytes below 0x80 are literal ASCII; bytes at or above it open a two-byte code.

Opens the name field.
D0 15
Closes the name, opens the description.

C0 3F

Why no font work is needed

The English payload uses exactly nine distinct codes: 8023 807C 9018 901B 901D 9024 B014 C03F D015. Integral’s Japanese item text uses 322 distinct codes, and all nine are among them. Integral also already renders raw ASCII in this very box — its own mine-detector message reads HARD, EXTREM in plain Latin — and the HUD short-name pool (STINGER, NO ITEM, C.BOX A, WEAPON) is English in the Japanese build.

Byte budget, and the hazard in the middle

The Japanese strings are not one clean run. A 116-byte island of unrelated data sits between the item and weapon pools, and the Integral-only MP 5 SD record sits immediately after the weapon pool. Both must survive.

80010EAC–80011674 Item description pool — 26 records 2,000 B · needs 1,684
80011674–800116E8 Do not touch: DIAZEPAM, MEDICINE, a 15-entry pointer array, PANEL MAKE Error, CLAYMORE 116 B
800116E8–80011B04 Weapon description pool — 10 records 1,052 B · needs 874
80011B04 Leave in place: MP 5 SD, Integral-only, reached by a lone pointer and absent from both tables 104 B

In-place overwrite is not quite enough

29 of the 36 English records fit inside the Japanese slot they replace. The other seven overflow by 74 bytes in total — and the slack that would absorb them is scattered as padding across the pool, in fragments too small to take a 78-byte cardboard-box record. Repacking each pool from its base and rewriting all 36 pointers avoids the fragmentation entirely.

That repack is safe because nothing else reaches into the pools: a scan for lui/addiu address pairs across the whole executable found zero code references into either range. The one string that is code-referenced is the mine-detector HARD/EXTREME message, whose English form needs 60 bytes against a 56-byte slot — so it moves into the weapon pool’s tail and its single lui/addiu pair at file 0x02BEB0/0x02BEB4 is repointed.

Getting bytes into the game

This is where the obvious approach fails. The address arithmetic below is correct, the PPF3 it produces is correct, Ketchup applies it and logs every byte — and the menu stays Japanese.

The arithmetic, which is not the problem

Ketchup’s ram_base for each Integral disc is exactly the raw-image offset of RAM 0x80010000. A 2,352-byte raw sector carries 2,048 bytes of user data, so every 2,048 bytes of executable advance 2,352 bytes of image:

k = exe_file_offset - 0x800                 # 0x800 = PS-EXE header
image_offset = ram_base + (k / 2048) * 2352 + (k % 2048)

ram_base:  0x131D2238  Integral disc 1   (/MGS/SLPM_862.47, LBA 136341)
           0x0EB38078  Integral disc 2   (/MGS/SLPM_862.48, LBA 104865)

Every one of the 62 resulting records was checked against an untouched retail image and matched the executable bytes exactly. Applied to a copy of that image, the re-extracted executable is identical to the intended output.

Why the disc patch cannot work

The Master Collection does not load MGS1’s executable from the CD image. It preloads it from a ROM snapshot — roms/mgs_integral_disc1-20230407.lz4a, a RAM image carrying the PS-EXE header at 0xB070 and the program at 0x10000. The CD image supplies the data files (STAGE.DIR, RADIO.DAT, DEMO.DAT…) and nothing else. That is why Konami’s own patch schema carries two independent targets, memory and disc: anything code- or text-resident has to go through memory.

The executable in RAM was verified against the retail build to be sure this was not a revision mismatch: the accelerator checksum reported at boot, 0x7FD6F607, is reproduced exactly by summing 256 words at file offset 0x800 of retail SLPM_862.47, and spot reads at four addresses match byte-for-byte. The one region that differs, around 0x9B000, is the BIOS-library block the Master Collection strips to 0xFF and replaces with its own acc_lib* accelerators.

Ketchup’s RAM mirror fires too early

Ketchup does attempt a RAM mirror alongside each CD write, which is the only path that could work here. It issues all 3,068 writes and logs each one, spanning 0x10EAE–0x9E5EC. Reading that RAM back once the game is playable, only 365 bytes of the item pool survive; the rest has reverted to the original Japanese, while the pointer tables stick. The restore happens in the setup that runs immediately after Ketchup — >>>setMemoryPatch, ### default patch MGS, EmuSRAM.capture_from_emu: success.

Writing the same 3,068 bytes later, straight into emulated RAM through g_emu_task.setRamValue, sticks — and the menu turns English. The guard on that mirror, while (!IsCdRomShellOpen()), and its comment — “if tray is open this isn’t a cold boot, so we can skip this” — show the design already anticipates a resident executable. Only the timing is wrong.

The fix, and the result

ApplyBlock() no longer writes RAM. It maps each block to its RAM address exactly as before but collects the writes into coalesced runs; a new Update(), called from _update_gadgets, verifies one byte per run every 30 frames and rewrites the set if anything has been clobbered. That makes it self-healing without needing to know what discards the early writes — which was never established. The CD-ROM write is untouched, because stage overlays and RADIO.DAT genuinely are read from the disc and always worked.

[Ketchup] loaded mods\INTEGRAL\INTEGRAL\0\INTEGRAL_disc1_en_items.ppf.
[Ketchup] Applied 3068 bytes of RAM patches in 54 blocks (pass 1).

One pass, all 54 blocks, and no re-apply since — so nothing is fighting it. The item and weapon descriptions read English through a plain PPF in the mods folder, surviving an ordinary launch with no debugger attached. The same repair applies to every other PPF mod that touches executable-resident bytes, which were all silently half-applying before.

Build pipeline

Each step below was run end-to-end against retail disc images; the numbering is the actual order of operations.

  1. Extract the images

    chdman extractcd to raw 2,352-byte-sector .bin for Integral discs 1–2, MGS1 (USA) discs 1–2 and VR Missions (USA).

  2. Pull the boot executables

    Walk ISO 9660 over the Mode 2 Form 1 sectors and dump SLPM_862.4x and SLUS_00x.xx.

  3. Read the donor tables

    26 item pointers at 800A0B38 and 10 weapon pointers at 800A0D24 in the USA executable, plus the special string at 800A0BA0.

  4. Repack into Integral’s pools

    Write the English records from each pool’s base in original address order, 4-byte aligned, zero-filling the remainder; then rewrite the 36 pointers and the one lui/addiu pair.

  5. Diff and emit

    Diff patched against original, split the changed runs on page and 255-byte limits, map each to an image offset, and write a PPF3 per disc. Result: 62 records, 3,068 patched bytes, a 3,686-byte patch file.

What is proven, and what is not

✓It renders. With the payload written into emulated RAM, Integral’s pause menu draws the English names and descriptions correctly. No font, glyph or renderer work was needed — confirmed on a running Master Collection build.
✓The worst cases fit. The widest description line in the set is 29 characters (Stinger Missile → “buttons and press ○ to fire.”) and the longest name is 26 (Remote-Controlled missile.). Both were forced onto a live item slot by repointing the tables, and both display cleanly — so nothing else in the set can overflow.
✓The offsets are right. All 62 patch records matched the corresponding executable bytes in an untouched retail image, and the patch round-trips: the re-extracted SLPM_862.47 is identical to the intended output.
✓Nothing else was clobbered. The island and the MP 5 SD record are untouched, no code references either pool, and RAM reads back byte-exact against the intended image across both pools and both tables.
✓Delivery is solved. With the deferred mirror in place the patch applies from an ordinary PPF in the mods folder and survives a normal launch, no debugger involved. Confirmed in-game on a built binary.
?The cause of the early discard was never identified. All 3,068 writes were issued and logged during disk-patch setup, and only 365 bytes survived — but the tray flag never flipped, so Ketchup’s own guard was not responsible. The fix works around it rather than explaining it, which is why it verifies and re-applies rather than writing once.
?One record has no English source. Integral’s MP 5 SD description exists in no localised build and stays Japanese unless it is written by hand. Its 104-byte slot is ample.

Three things that cost time

Each of these is a trap in the tooling rather than in the data, and each fails silently.

  • Ketchup half-applies patches to executable-resident data. Its RAM mirror runs before the Master Collection finishes setting up machine memory, so most of it is discarded — but every byte is logged as written, so the log reports total success. Any PPF mod that touches the executable is affected, not just this one.
  • sqdbg’s receive buffer is 1,024 bytes, not MAX_MSG_LEN. sq_rdbg_update reads into char temp[1024] and breaks at size >= sizeof(temp)-2, so any ev: message over ~1,022 bytes is truncated and fails to compile. The reply is a bare XML header with no <eval> element — indistinguishable at a glance from an expression that returned nothing. The MAX_MSG_LEN 2049 in the header is misleading.
  • Integers returned from native calls fail ==. g_emu_task.getRamValue(16, 0x10EAE) reports typeof “integer”, prints as 30035, satisfies > 30034 && < 30036, and v - 30035 is 0 — yet v == 30035 is false. Passing it through an arithmetic op first (local w = v + 0) restores ==. It looks like upper bits surviving in the SQInteger on x64, and it quietly breaks every comparison written the obvious way — a RAM search that should have hit returns nothing at all.

Menu text: the rules, and one difference you cannot fix

Menu strings live in STAGE.DIR as GCL records — 07 <length> <payload> 00 — and are read from the disc at stage load, so a plain PPF reaches them. Four rules came out of getting one string wrong in four different ways.

  1. Rewrite payload bytes only — unless you also fix the four fields that track the chain’s size.

    Shrinking one record by 5 bytes once painted a row of dashes across every help line on the screen, including untouched ones. The cause is now known and is listed in full under the stage container: three container sizes in the script, listed in full under the stage container - and two fields that must be left exactly as retail. Fix those and a record can be grown safely; leave them and the script derails.

  2. Raw ASCII is fine — one byte per character.

    Integral mixes encodings: NEW GAME is raw ASCII while OFF two records away is fullwidth 804F 8046 8046. Since English costs a byte a character, it comfortably fits slots sized for Japanese.

  3. Terminate with an embedded NUL; never pad the visible string.

    The renderer stops at the first NUL but the interpreter skips by the length byte, so writing TEXT 00 <filler> keeps the record's footprint while rendering the string unpadded. Padding is not ignored: every trailing space pushes the text about 18 px left, so five of them put a nine-character string 90 px out of place.

  4. Match slots by their Japanese bytes, not by index.

    The record order differs between stages and between builds: the same five disc-swap prompts appear in three different orders across title, change and demosel. Lifting the signature bytes out of the retail image and matching on the whole payload removes the guesswork — and catches prefix collisions, such as Meryl’s slot also matching Red Meril’s.

The help line is right-aligned, and the two builds disagree by 18 px

The difficulty help text is not centred. It is pinned by its right edge, and the two releases pin it in different places:

The mismatch is documented here rather than fixed, deliberately.

The stage container and the GCL script format

Making a string longer broke something else on screen every time until the script format was read out of FoxdieTeam/mgs_reversing rather than inferred. Everything below is from source/libgcl, checked against the executable’s own decoder.

STAGE.DIR and stages

A u32 header size, then 12-byte entries: an 8-byte name and a u32 sector offset relative to STAGE.DIR’s first sector. Integral disc 1 has 95 entries; the last, ending, begins at byte 1,132 and so runs past the declared header size — a header_size / 12 walk stops at 94 and wrongly reports free space at EOF.

A stage is a 2048-byte header then chunks in header order, each padded to 2048; the span is exactly 2048 plus the sum of the padded sizes, on every stage checked. The header is u16 flag, u16 size_in_sectors, then 8-byte entries of u32 size, u16 flags, char[2] tag. Only nd, ck, sw, se and the zero-tag terminator hold inline data; cl/ch/cg carry sizes but no bytes.

stage_lookup (0x80022DCC) returns entry_offset + stagedir_base_lba — a plain 32-bit add with no bound. Its caller reads one sector; the callback at 0x80023274 takes the sector count from lh [header+2] and reads the rest. A stage’s length comes from its own header and nothing else.

What to change when a string grows

Parse the script top-down and take the sized nodes whose span encloses the edit. For option and preope that is three fields, and their retail values differ between Integral and the USA build by exactly the chain-size delta:

Two fields that must be left exactly as retail. The GCL_OPTION length byte at script+0x1B4 should be chain_span + 4 but is only 8 bits and has already overflowed in the shipped game (91 for a 599-byte chain, 154 for a 10,134-byte one). And for option, the stage header’s chunk size: updating it is what crashed three separate builds. That chunk is the last in the stage, so nothing downstream depends on its declared length, and retail’s value is the one that works.

Verify by re-parsing the patched bytes top-down and requiring a clean decode. Checking that the numbers match the USA build proves nothing — two builds passed that test and then crashed.

The decompilation changes the approach

FoxdieTeam/mgs_reversing targets Metal Gear Solid Integral specifically — SLPM_862.47/.48, the exact executables on these discs — and builds byte-matching output. That turns binary archaeology into source edits.

✓It reproduces the discs exactly. Built preope.bin (24,911 bytes) and option.bin (25,842 bytes) are byte-for-byte identical to the nd chunks on disc. That is the guarantee the whole approach rests on: from a verified baseline, any difference in output is provably only the change made.
✓The toolchain fails on long paths. asmpsx.exe is a 1990s tool that dies with an access violation (0xC0000005) at a fixed instruction with a garbage address when paths get long — which is why the project’s CI clones to c:\mgs. From a ~150-character scratchpad path: 32 failures. From D:\mgsbuild\d: 45/45, zero failures.
✓Only the overlays you need have to build. ninja ../obj/preope.bin ../obj/option.bin skips the handful of files that still fail elsewhere in the tree.

Previous Operations: half of it fits

The English recap is 9,441 characters against Integral’s 8,214. It does not fit — but that is a space budget, not a bug, and once the budget is written down one half of the recap fits comfortably inside it.

The page count is declared three times

Two of them are the PAGE_COUNT defines; the third is easy to miss and was the cause of every crash:

#define PAGE_COUNT  9                     // pre_met1.c - Metal Gear
#define PAGE_COUNT  14                    // pre_met2.c - Metal Gear 2

Unknown field_714[72];                    // preope.c - AGAIN, as a literal
Unknown field_4614[112];
for (j = 0; j < 9;  j++) ...              // and again in the parse loops
for (j = 0; j < 14; j++) ...

Changing only the two defines leaves preope.c reading 72 + 112 strings out of a longer chain, and everything downstream misaligns. Fixing all three took the failure from 220 MB of mainbus_read_l: bad addr to zero.

The layouts also differ between builds: USA uses 7 lines per page (13 and 19 pages = 91 + 133 lines), Integral uses 8 (9 and 14 = 72 + 112). At Integral’s 8, the same English text needs 12 and 17 pages.

The stage cannot grow

Proven two ways. Empirically: byte-identical content with only the sector count changed 87→88 freezes, while the same content at 87 sectors relocated into DUMMY3M.DAT runs fine. And in the source:

buffer = GV_GetMaxFreeMemory( GV_NORMAL_MEMORY );   // largest free block
task->size = datacnf->size * 512;                   // sb.size sectors, read into it

The stage is read into the largest free heap block, and 87 sectors evidently fills it. So relocation works but growth does not, and the chain can only expand into the script chunk’s own 796 bytes of internal padding.

The option screen’s 21-character buffer

Porting use directional buttons to test works — the text renders and the script executes cleanly — but it corrupts that row of the screen. The cause is in the option screen’s own code, not in the data.

rect.w = 64;                                       // opt.c, every option string
font_set_kcb(kcb, -1, -1, 0, 6, 2, 0);
w = (kcb->rect_ptr->w * 4) / (kcb->c_skip + 12);    // font.c -> 64*4/12 = 21

Each option string gets a buffer holding 21 characters on one line. The retail Japanese line is 13 glyphs and fits; use directional buttons to test is 31 and spills into neighbouring VRAM. The columns make it worse — they are placed at x = 832 and 896, exactly rect.w apart, so anything wider lands on the next column.

What VR Missions (USA) is actually for

It cannot serve as the donor for discs 1–2 — but it is the most useful reference disc in the set, and it is the exact donor for disc 3.

  • It is two records short. Its tables hold 24 items, not 26: the frozen Ketchup and frozen Rations variants the main game needs simply are not there. MGS1 (USA), with all 26 items and all 10 weapons, is the complete donor.
  • It proves the Integral-generation engine speaks Latin. Five language blocks run through one pair of tables with a language index, using the same B014/D015/807C grammar plus 1Fxx for accented letters. Its item pool starts at 80010EA0, twelve bytes from Integral’s 80010EAC, and the two builds share roughly twice as much byte-identical code as either shares with MGS1 (USA).
  • It supplies tighter English. Its English block is otherwise the same text as MGS1 (USA)’s, but with names trimmed to fit — useful the moment a name overruns.
  • It is the 1:1 donor for Integral disc 3. VR Missions (USA) is the localised VR-Disk, so the same method aimed at Ketchup’s INTEGRAL\VR-DISK folder is a straight table-for-table transplant, with a language index already in place.
  • Its extended-Latin escapes are the route to other languages. Anyone wanting Integral in Spanish, Italian, French or German has both the text and the glyph codes in this one executable.

Two obstacles in the build, worth keeping

Neither is in the fix itself, and both will catch the next person.

build_zydis.cmd breaks on any path containing a space. It tests if not exist %ZY_PROJECT% and invokes msbuild %ZY_PROJECT% unquoted, so a checkout under, say, My Drive makes cmd split the path and the script reports the Zydis project file missing when it is sitting right there. Zydis pins v143. The project targets v145, so a machine with only the 2026 Build Tools cannot build the dependency as configured. Pre-building Zydis with v145 and writing its .zydis_build_hash makes the cache check skip it, leaving both the static library and the ASI on one toolset. Note that CI sidesteps this from the other direction, overriding everything to v143.
